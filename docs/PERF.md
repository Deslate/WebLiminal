# 性能基线与优化目标

## 基线（未优化）

**测量条件**：M3 Max、**本机无其它 GPU 占用**（用户未运行游戏）、视口 1280×832、**内部分辨率档位固定**（不是动态分辨率）。

| 内部分辨率 | 帧率 |
|---|---|
| 50% | 待补（用户体感"还行"） |
| **70%** | **15–16fps** |
| **100%** | **约 10fps**（日志原始值：`opening 10.50`、`door 9.30`） |

**重要提醒**：此前多次汇报的 35–45fps 是**动态分辨率**下的数字——内部尺寸被自动降下来之后的结果。**固定档位的真实开销远高于此**，不能混用。

## 硬约束（任何优化都必须满足）

- 默认档观感**逐值不变**（标准截图 + 完整 76 秒路线的亮度值对照）；
- **采样数量 / 反射透射路径 / 光能计算不许降**；
- 汇报**固定档位**的真实帧率，**不许拿动态分辨率的数字充数**。

## 目标

- **70% ≥ 40fps**；
- **100% 尽量 ≥ 30fps**。

## 本轮所做的优化（Sonnet 5，2026-09-30）

**开销分解（实测，config.profile 的 GPU 完成时间三段计时，已与连续渲染 10 秒窗口的真实 fps 交叉核对，两者一致在 3% 以内）**。100% 分辨率、door 视角、机器空闲时：

| 排名 | 阶段 | 每帧耗时 | 占比 |
|---|---|---|---|
| 1 | **相机路径追踪主通道**（`camera.wgsl` 的 `camera` compute pass，含全部反射/直接光/阴影） | **~83ms** | ~86% |
| 2 | 每帧水光/漫反射更新（`emitWater`/`waterHorizontal`/`waterResolve`/`restrictPatches`/`propagate`/`compose`） | ~9.6ms | ~10% |
| 3 | 波浪模拟（FFT 等） | ~4.0ms | ~4% |
| （其余） | 反射降噪 2 道 + 呈现 present | ~1.0ms | ~1% |

（曾用 GPU timestamp query 直接测各 pass，测出 `display`/present 通道耗时和 `camera` 通道相当——用两段式 CPU 计时交叉验证后确认那是**仪器伪影**：对渲染到 canvas 的 render pass 加时间戳查询会人为拉长其读数，真实 present 开销 <1ms。已改用 `config.profile` 的分段 `await device.queue.onSubmittedWorkDone()` 计时，可信。）

对相机通道本身做开关消融（同一视角，逐项关闭一个特性，测剩余耗时）：

| 关闭的部分 | 剩余耗时 | 该部分占相机通道比例 |
|---|---|---|
| 48/64 束粗糙反射续追（`radiance()` 里那层 GGX 二级光线循环） | 9.05ms | **~89%** |
| 缝隙微阴影步进 `jointVisibility`（32 步高度场行进，每次直接光计算调 2 次） | 63.16ms | ~24% |
| 天窗面积光项（含其内部一次 `jointVisibility`） | 66.45ms | ~20% |
| 瓷砖浮雕行进 `reliefHit` | 79.41ms | ~4% |

**结论：相机通道的开销几乎全部来自"二级反射光线数 × 每条光线的着色成本"这个乘积**，而不是任何单一环节。二级光线数（48/64 束、每像素 2–8 个自适应主样本）是**硬约束明令不许降的量**，所以能动的只有"每条二级光线的着色成本"这个因子。

**做了什么（均已用完整 76 秒路线的逐值比对验证，见下）**：

1. **推迟命中属性计算**（`src/render/common.wgsl` 的 `traceSolid`）：原来在场景求交的扫描过程中，每次找到一个比当前最近的候选更近的命中，就立刻调用 `makeHit()` 算出完整 `Hit`（含材质 UV，需要一次除法和图册缓冲读取），即使这个候选后续会被更近的候选取代。改为扫描过程中只记录获胜候选的标量（t / 法线 / 形状 / 面），扫描结束后只对最终获胜者调用一次 `makeHit()`。对任何调用都不会更贵，经常更便宜。
2. **专用遮挡查询**（新增 `traceSolidAny` / `traceBodyAny` / `traceDynamicSolidAny`）：阳光阴影射线（`directLighting` 的太阳项，在二级反射循环里按每条光线调用一次）、`sky.wgsl` 的天窗可见性积分、`water-caustics.wgsl` 每帧的太阳/天窗水面可见性判断，原先都调用"找最近命中"的 `traceSolid`/`traceDynamicSolid`，只用其 `.t` 做布尔判断。新函数命中即返回 `true`，不组装 `Hit`、不继续扫描剩余形状。经代数验证与原布尔结果逐位等价（含 `water-caustics.wgsl` 里 `maxT` 和判断阈值不同的那个 `.005` 容差写法，已核对等价）。
3. **共享缝隙微阴影的命中态预处理**（`jointVisibility` 拆成 `jointVisibilityPrepare` + `jointVisibilityMarch`）：原来 `directLighting` 对同一个命中点 `h`、两个不同方向（太阳、天窗中心）各调一次 `jointVisibility`，其中与方向无关的部分（瓷砖坐标系、早退条件、行进起始高度）被重复算了两遍。拆分后按需惰性计算一次并在两次方向查询之间共享；两个分支都不需要时（暗侧且天窗积分为零）则一次也不算，只多不少地等于原开销。

**这三条都不改变任何数值结果**，只改变"怎么算出同一个结果"。

## 正确性验证（硬约束 1）

用 `scripts/roam-v149.mjs`（即 `npm run benchmark` 内部用的同一条 76 秒 / 2280 帧漫游路径与相机 API）分别捕获改动前（`git show HEAD:...` 提供原始 4 个文件）与改动后（当前工作区）的逐帧亮度数组：

- **607,027,200 个亮度值中，改动前后只有 1 个不同，且仅差 1/255**（frame 263, (y=84,x=526)，一处接近全黑的暗部像素：7→8）。两次独立重跑（先做完①再叠加③、以及只做①两种代码状态）都是同一个像素、同一帧、同一幅度，说明这是 GPU 着色器编译器重排浮点运算导致的确定性舍入噪声，不是逻辑错误——量级与 `docs/STABLE.md` 里已经记录的"门洞转身 100ms 差分 p99=3/255"同一个噪声地板;
- 每 10 秒采样一次的标准截图（共 5 张核对）**逐字节相同**。

**采样数量 / 反射透射路径 / 光能计算**：未触碰。48/64 束反射方向数、2–8 档自适应主样本数、256 点天窗积分、128 方向漫反射链接、光子数/批次数等全部原样保留（`grep` 确认改动只落在 `common.wgsl`/`camera.wgsl`/`sky.wgsl`/`water-caustics.wgsl` 四个文件，且每处都只是"何时/是否组装 `Hit` 结构体"或"两次调用间共享一份无方向依赖的预处理"）。

## 分档实测表（硬约束 3、4）

**重要限制**：本轮测量期间，本机持续有**其它应用占用 GPU**（`ioreg -c AGXAccelerator` 读到 `Device Utilization %` 持续 97–100%，来源是当时开着的常规 Chrome 窗口 / 一个 Electron 应用 / 微信小程序 GPU 进程等，不是游戏，但同样构成 PERF.md 基线要求排除的"其它 GPU 占用"）。这使得**本轮测出的绝对 fps 数字不能和文档开头"机器空闲"下测的基线数字直接比较**——例如波浪模拟这个完全没动过代码的环节,本该 ~4ms,本轮测量中却在 14–49ms 之间跳动。

为了在这种环境噪声下仍然拿到关于"这次改动有没有用、有多少用"的可信数字，改前/改后使用同一个脚本、同一个浏览器会话、只用 `page.route` 切换四个文件的内容（`git show HEAD:...` 版本 vs 当前工作区版本，不触碰磁盘/不触发 dev server 重载),紧邻测量,消去环境漂移造成的偏差:

| 分辨率 | 视角 | 相机通道 改前→改后 | 相机通道变化 | 总耗时 改前→改后（含噪声） | fps 改前→改后（含噪声） |
|---|---|---|---|---|---|
| 50% | opening | 47.0→42.8ms | **-8.9%** | 94.6→93.0ms | 10.57→10.76 |
| 50% | door | 55.6→50.6ms | **-9.0%** | 98.5→97.8ms | 10.15→10.23 |
| 70% | opening | 64.1→57.3ms | **-10.5%** | 113.5→110.1ms | 8.81→9.09 |
| 70% | door | 80.7→71.6ms | **-11.3%** | 119.6→119.4ms | 8.37→8.37 |
| 85% | opening | 76.3→72.2ms | **-5.4%** | 128.6→126.5ms | 7.78→7.90 |
| 85% | door | 98.7→91.7ms | **-7.1%** | 137.7→137.7ms | 7.26→7.26 |
| 100% | opening | 95.6→91.0ms | **-4.8%** | 147.1→144.8ms | 6.80→6.91 |
| 100% | door | 130.4→127.3ms | **-2.4%** | 159.4→162.4ms | 6.27→6.16 |

"总耗时/fps"列里的噪声（外部 GPU 占用）经常比本次优化的信号还大（见 100%/door 那行：相机通道确实降了 2.4%，但总耗时反而因为波浪模拟那次刚好撞上更重的外部负载而"变差"了）——**这一列不能当作本次改动效果的证据，只有"相机通道"这一列是本次改动的直接测量**。

把"相机通道"这一列的改善幅度，套用到本会话最初、机器基本空闲时测到的基线（与 `docs/PERF.md` 顶部记录的 15–16fps/70%、~10fps/100% 吻合）上做外推估算（**这是估算，不是实测**，留给用户在机器空闲时用 `EVIDENCE_DIR=... node scripts/profile-fixed-v162.mjs`（`PROFILE=0`）重新实测确认）：

| 分辨率 | 视角 | 原始基线 fps（机器空闲） | 估算改动后 fps |
|---|---|---|---|
| 70% | opening | 18.0 | ~19.6 |
| 70% | door | 15.8 | ~17.4 |
| 100% | opening | 12.1 | ~12.6 |
| 100% | door | 10.3 | ~10.6 |

## 哪条没做到

**没有达到 70% ≥ 40fps、100% ≥ 30fps 的目标**。原因不是本轮优化没做对，而是**架构性的**：

- 相机通道 89% 的开销就是"每像素 2–8 个主样本 × 每个上釉命中 48/64 束二级反射光线 × 每条二级光线一次完整求交与着色"这个乘积本身，不是某个可优化掉的旁枝；
- 本轮做的三处改动都是**只降低"每条光线的常数开销"**（避免多余的 `Hit` 组装、避免不必要的最近命中搜索、避免重复的无方向依赖预处理），量级上只能拿到 **个位数到十几个百分点**的相机通道加速；
- 要达到 40fps/70% 需要的是相对 70% 当前 ~18fps 基线约 **2.2 倍**的总加速、100% 需要相对 ~10-12fps 基线约 **2.5-3 倍**——这个量级只能来自"减少二级光线数量"或"降低每像素主样本数"，而这两条正是本任务**硬约束明令不许动**的量。
- 因此在"采样数量 / 反射透射路径 / 光能计算不许降"这条约束下，我判断**当前这套路径追踪架构下，仅靠本轮这类不改变结果的常数因子优化，无法达到 40fps/70%、30fps/100% 的目标**；要真正达标需要用户重新权衡是否放开某条硬约束（例如：允许二级反射光线做屏幕空间缓存/时间摊销而不是每帧每样本重新全采样——但这会改变"每帧独立、无历史"的现有语义，需要用户明确批准）。

## 当前状态

- 已完成：`traceSolid` 推迟命中属性计算、新增专用遮挡查询（`traceSolidAny`/`traceBodyAny`/`traceDynamicSolidAny`）并接入 3 处调用点、`jointVisibility` 预处理去重；
- 已验证：76 秒 / 2280 帧逐值比对（607,027,200 个值中 1 个差 1/255，可复现、可解释为浮点重排噪声）、标准截图逐字节相同、采样/光线数量未改动；
- 已测量：相机通道在 8 个分辨率×视角组合下全部**变快**（-2.4% 到 -11.3%），未观察到任何一处变慢；
- 未达成：70% ≥ 40fps、100% ≥ 30fps 的目标（见上"哪条没做到"）；
- 本轮测量环境有外部 GPU 占用干扰，建议机器空闲时用 `node scripts/profile-fixed-v162.mjs`（`PROFILE=0`）复测绝对 fps。
