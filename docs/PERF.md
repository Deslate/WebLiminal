# 性能基线与优化目标

## 基线（未优化）

**测量条件**：M3 Max、**本机无其它 GPU 占用**（用户未运行游戏）、视口 1280×832、**内部分辨率档位固定**（不是动态分辨率）。

| 内部分辨率 | 帧率 |
|---|---|
| 50% | 待补（用户体感"还行"） |
| **70%** | **15–16fps** |
| **100%** | **约 10fps**（日志原始值：`opening 10.50`、`door 9.30`） |

**重要提醒**：此前多次汇报的 35–45fps 是**动态分辨率**下的数字——内部尺寸被自动降下来之后的结果。**固定档位的真实开销远高于此**，不能混用。

## 硬约束（任何优化都必须满足）

- 默认档观感**逐值不变**（标准截图 + 完整 76 秒路线的亮度值对照）；
- **采样数量 / 反射透射路径 / 光能计算不许降**；
- 汇报**固定档位**的真实帧率，**不许拿动态分辨率的数字充数**。

## 目标

- **70% ≥ 40fps**；
- **100% 尽量 ≥ 30fps**。

## 本轮所做的优化（Sonnet 5，2026-09-30）

**开销分解（实测，config.profile 的 GPU 完成时间三段计时，已与连续渲染 10 秒窗口的真实 fps 交叉核对，两者一致在 3% 以内）**。100% 分辨率、door 视角、机器空闲时：

| 排名 | 阶段 | 每帧耗时 | 占比 |
|---|---|---|---|
| 1 | **相机路径追踪主通道**（`camera.wgsl` 的 `camera` compute pass，含全部反射/直接光/阴影） | **~83ms** | ~86% |
| 2 | 每帧水光/漫反射更新（`emitWater`/`waterHorizontal`/`waterResolve`/`restrictPatches`/`propagate`/`compose`） | ~9.6ms | ~10% |
| 3 | 波浪模拟（FFT 等） | ~4.0ms | ~4% |
| （其余） | 反射降噪 2 道 + 呈现 present | ~1.0ms | ~1% |

（曾用 GPU timestamp query 直接测各 pass，测出 `display`/present 通道耗时和 `camera` 通道相当——用两段式 CPU 计时交叉验证后确认那是**仪器伪影**：对渲染到 canvas 的 render pass 加时间戳查询会人为拉长其读数，真实 present 开销 <1ms。已改用 `config.profile` 的分段 `await device.queue.onSubmittedWorkDone()` 计时，可信。）

对相机通道本身做开关消融（同一视角，逐项关闭一个特性，测剩余耗时）：

| 关闭的部分 | 剩余耗时 | 该部分占相机通道比例 |
|---|---|---|
| 48/64 束粗糙反射续追（`radiance()` 里那层 GGX 二级光线循环） | 9.05ms | **~89%** |
| 缝隙微阴影步进 `jointVisibility`（32 步高度场行进，每次直接光计算调 2 次） | 63.16ms | ~24% |
| 天窗面积光项（含其内部一次 `jointVisibility`） | 66.45ms | ~20% |
| 瓷砖浮雕行进 `reliefHit` | 79.41ms | ~4% |

**结论：相机通道的开销几乎全部来自"二级反射光线数 × 每条光线的着色成本"这个乘积**，而不是任何单一环节。二级光线数（48/64 束、每像素 2–8 个自适应主样本）是**硬约束明令不许降的量**，所以能动的只有"每条二级光线的着色成本"这个因子。

**做了什么（均已用完整 76 秒路线的逐值比对验证，见下）**：

1. **推迟命中属性计算**（`src/render/common.wgsl` 的 `traceSolid`）：原来在场景求交的扫描过程中，每次找到一个比当前最近的候选更近的命中，就立刻调用 `makeHit()` 算出完整 `Hit`（含材质 UV，需要一次除法和图册缓冲读取），即使这个候选后续会被更近的候选取代。改为扫描过程中只记录获胜候选的标量（t / 法线 / 形状 / 面），扫描结束后只对最终获胜者调用一次 `makeHit()`。对任何调用都不会更贵，经常更便宜。
2. **专用遮挡查询**（新增 `traceSolidAny` / `traceBodyAny` / `traceDynamicSolidAny`）：阳光阴影射线（`directLighting` 的太阳项，在二级反射循环里按每条光线调用一次）、`sky.wgsl` 的天窗可见性积分、`water-caustics.wgsl` 每帧的太阳/天窗水面可见性判断，原先都调用"找最近命中"的 `traceSolid`/`traceDynamicSolid`，只用其 `.t` 做布尔判断。新函数命中即返回 `true`，不组装 `Hit`、不继续扫描剩余形状。经代数验证与原布尔结果逐位等价（含 `water-caustics.wgsl` 里 `maxT` 和判断阈值不同的那个 `.005` 容差写法，已核对等价）。
3. **共享缝隙微阴影的命中态预处理**（`jointVisibility` 拆成 `jointVisibilityPrepare` + `jointVisibilityMarch`）：原来 `directLighting` 对同一个命中点 `h`、两个不同方向（太阳、天窗中心）各调一次 `jointVisibility`，其中与方向无关的部分（瓷砖坐标系、早退条件、行进起始高度）被重复算了两遍。拆分后按需惰性计算一次并在两次方向查询之间共享；两个分支都不需要时（暗侧且天窗积分为零）则一次也不算，只多不少地等于原开销。

**这三条都不改变任何数值结果**，只改变"怎么算出同一个结果"。

## 正确性验证（硬约束 1）

用 `scripts/roam-v149.mjs`（即 `npm run benchmark` 内部用的同一条 76 秒 / 2280 帧漫游路径与相机 API）分别捕获改动前（`git show HEAD:...` 提供原始 4 个文件）与改动后（当前工作区）的逐帧亮度数组：

- **607,027,200 个亮度值中，改动前后只有 1 个不同，且仅差 1/255**（frame 263, (y=84,x=526)，一处接近全黑的暗部像素：7→8）。两次独立重跑（先做完①再叠加③、以及只做①两种代码状态）都是同一个像素、同一帧、同一幅度，说明这是 GPU 着色器编译器重排浮点运算导致的确定性舍入噪声，不是逻辑错误——量级与 `docs/STABLE.md` 里已经记录的"门洞转身 100ms 差分 p99=3/255"同一个噪声地板;
- 每 10 秒采样一次的标准截图（共 5 张核对）**逐字节相同**。

**采样数量 / 反射透射路径 / 光能计算**：未触碰。48/64 束反射方向数、2–8 档自适应主样本数、256 点天窗积分、128 方向漫反射链接、光子数/批次数等全部原样保留（`grep` 确认改动只落在 `common.wgsl`/`camera.wgsl`/`sky.wgsl`/`water-caustics.wgsl` 四个文件，且每处都只是"何时/是否组装 `Hit` 结构体"或"两次调用间共享一份无方向依赖的预处理"）。

## 哪条没做到

**没有达到 70% ≥ 40fps、100% ≥ 30fps 的目标**。原因不是本轮优化没做对，而是**架构性的**：

- 相机通道 89% 的开销就是"每像素 2–8 个主样本 × 每个上釉命中 48/64 束二级反射光线 × 每条二级光线一次完整求交与着色"这个乘积本身，不是某个可优化掉的旁枝；
- 本轮做的三处改动都是**只降低"每条光线的常数开销"**（避免多余的 `Hit` 组装、避免不必要的最近命中搜索、避免重复的无方向依赖预处理），量级上只能拿到 **个位数到十几个百分点**的相机通道加速；
- 要达到 40fps/70% 需要的是相对 70% 当前 ~18fps 基线约 **2.2 倍**的总加速、100% 需要相对 ~10-12fps 基线约 **2.5-3 倍**——这个量级只能来自"减少二级光线数量"或"降低每像素主样本数"，而这两条正是本任务**硬约束明令不许动**的量。
- 因此在"采样数量 / 反射透射路径 / 光能计算不许降"这条约束下，我判断**当前这套路径追踪架构下，仅靠本轮这类不改变结果的常数因子优化，无法达到 40fps/70%、30fps/100% 的目标**；要真正达标需要用户重新权衡是否放开某条硬约束（例如：允许二级反射光线做屏幕空间缓存/时间摊销而不是每帧每样本重新全采样——但这会改变"每帧独立、无历史"的现有语义，需要用户明确批准）。

## 第二轮：70% 档、硬约束不放开的前提下还有没有结构性空间（Sonnet 5，2026-09-30）

用户问题：第一轮只压了"每条光线的常数开销"，除此之外，**求交本身（BVH/访存/发散）、占用率、重复工作、可预计算、数值简化**这几类，各自有没有空间？逐项排查，每项都实测，查不出空间的也要给出数字。

### 1. 求交本身：没有 BVH，场景只有 13 个解析形状

`src/render/geometry.js` 的 `add(...)` 一共调用 **13 次**——房间的地板/四面墙、天窗开口的四块遮片、三个泳池拱洞、一条走廊拱洞、两小块台阶。`traceSolid`/`traceSolidAny` 对这 13 个形状做的是**线性扫描 + 提前剪枝**（`tn>bestT` 一命中就让后续形状的包围盒测试变成几次减法/比较，不会展开到形状内部几何）。

**没有建 BVH，也不该建**：BVH 在图形学里公认的收支平衡点是几十到几百个图元起，遍历本身的指针追逐/多级包围盒测试开销，在 13 个图元这个量级下会比直接线性扫描更贵，不是更省。13 个 `Shape`（每个 64 字节）总共 832 字节，整个数组在一次 warp 内广播读（同一 workgroup 里所有线程按相同顺序访问相同下标），远小于任何一级缓存——**访存布局（AoS/SoA）在这个规模下也不构成瓶颈**，没有实现 SoA 版本去验证，因为这个结论的不确定性足够低（数据量小两个数量级，不是"测出来才知道"的边界情况）。

### 2. 占用率：重新测过 workgroup size，8×8 已经是最优附近，不是没测到位

第一次测 workgroup size 时得到过一个看起来巨大的信号（`1×64` 比 `8×8` 快 5.5 倍）——**这个信号是假的**：改 `@workgroup_size` 时忘了同步改 `renderer.js` 里硬编码的 `dispatchWorkgroups(Math.ceil(width/8), Math.ceil(height/8))`，导致非 8 的倍数配置**实际只覆盖了画面的一部分**（截了张图验证，`1×64` 下右边 88% 的画面是从未写入的黑色）。发现后改成同步патch 两个文件、并且截图比对确认覆盖完整再计时，重新测：

| workgroup 形状 | 相机通道耗时（door、100%，同一浏览器会话内测） | 画面是否完整（与 8×8 截图逐字节比对） |
|---|---|---|
| **8×8（当前值）** | **88.54ms** | — |
| 4×4 | 155.92ms | 是 |
| 8×4 / 4×8 | 90.31ms / 89.89ms | 是 |
| 2×8 / 8×2 | 159.61ms / 158.30ms | 是 |
| 16×4 / 4×16 | 96.07ms / 88.40ms | 是 |
| 2×16 / 16×2 | 97.71ms / 98.02ms | 是 |
| 1×64 / 64×1 | 121.50ms / 109.28ms | 是 |
| 1×32 / 32×1 | 121.97ms / 113.82ms | 是 |
| 16×8 / 8×16 | 91.36ms / 85.26ms | 是 |

**结论：8×8 已经在最优附近**（4×16 与 8×16 基本打平，差 <1ms），所有"瘦长"配置（1 宽/1 高，或 2 宽）都明显更差，很可能是 `image`/`reflectionLayer` 按行存储、写入合并（coalescing）在瘦长 workgroup 下变差抵消了任何占用率收益。**这条确认没有空间**，且这次是用会改变输出正确性的错误方法先得到了假阳性，已经在报告里如实记录这个教训。

### 3. 重复工作：在 `tileProfile` 里找到两处真实的重复/死计算，已修

`tileProfile` 是全渲染器里被调用最多的函数之一：`reliefHit` 的瓷砖浮雕行进循环里每次命中最多调 128 次，`jointVisibilityMarch` 的缝隙微阴影行进循环里最多调 32 次（每个命中点两个方向各一次），材质着色里再调 1-2 次。逐行核对这个函数的返回值 `TileProfile{height,edge,id,bevel,slope}` 在所有调用点分别用到了哪些字段，发现：

- **`r.z`/`r.w` 两路 `hash2()` 结果算出来后，整个函数里没有任何地方读取过**——死代码。删除后只保留 `r.x`/`r.y`（用于 tilt/bevel）。
- **`let angle=0.;` 之后现算的旋转矩阵 `rotation=mat2x2f(cos(angle),-sin(angle),sin(angle),cos(angle))` 恒等于单位矩阵**（没有任何代码路径把 `angle` 设成别的值）——`q=rotation*local` 和后面 `slope=transpose(rotation)*(...)` 两处矩阵乘法都在做"乘以单位矩阵"这件事。改成 `q=uv-center` 直接赋值，`slope` 那行去掉 `transpose(rotation)*` 包装。

**实测（door、100%，同一浏览器会话内交替测 3 轮，取相机通道均值）**：

| 改动 | 3 轮相机通道变化 |
|---|---|
| 只删 `r.z`/`r.w` 死代码 | -4.5% / -4.6% / -3.3% |
| 再叠加去掉恒等旋转矩阵 | -1.1% / -1.4% / -0.4%（叠加在上一步之上） |

**`r.z`/`r.w` 那条是本轮单项最大的、独立确认的真实收益**；恒等旋转矩阵那条收益很小，大概率是因为 `cos(0.)`/`sin(0.)` 这种编译期常量参数的三角函数，WGSL/Metal 编译器本来就常量折叠掉了大半，手改代码主要是让意图更清楚，不是白测——但也如实报告：**"看起来明显浪费"不代表"编译器还没优化掉"，两者要分开验证**，这也是为什么第 5 类（数值简化）我全部做了实测而不是凭直觉判断。

其它检查过的"重复"没有发现空间：主/二级光线打到的是不同的命中点，太阳阴影射线在 48/64 束循环里是对不同点各查一次，不是同一(点,方向)重复查询；`sunDirection()`/`sunIrradiance()` 是对常量/uniform 的轻量读取，量级远小于上面两处。

### 4. 可预计算：查过、判断不能做

天窗面积光（`skyIntegral`）已经是每次场景重置时预烘焙一次、每帧只做双线性查表——这条已经是对的。**唯一还在"每帧/每条二级光线现算"的是太阳阴影可见性**（`directLighting` 里对静态几何的 `traceSolidAny(ro,sun,INF)`），它只依赖命中点位置和太阳方向（都不随帧变化）,理论上可以像 `skyIntegral` 一样按表面网格烘焙一次。**没有做，原因是这会改变结果**：太阳可见性是硬边界（要么被挡要么不被挡，`jointVisibility` 只处理瓷缝那种毫米级软化），按固定网格烘焙、帧内再双线性插值,会在每一条阴影边界上引入**空间量化误差**——这正是 `docs/STABLE.md` 里已经明确修过的"用单格照度代表大范围漫反射单元"的欠采样问题的同类错误，会直接违反"逐值不变"。判断这条不能在不违反硬约束的前提下做。

### 5. 数值简化：测了 schlick 的 `pow(x,5)`，实测有收益但改变了太多像素值，撤销了

`schlick(c,f0)=f0+(1-f0)*pow(1-clamp(c,0,1),5.)` 在整个渲染器里被调用得非常频繁（每次 `directLighting`、每次水面菲涅尔）。把 `pow(x,5.)` 换成重复乘法 `x2=x*x; x2*x2*x`：

- **性能**：早期一轮消融测到 -5.4%（85.17→80.57ms）；机器有其它 GPU 占用时重测,信号被噪声盖住（124.91→124.31ms，~0）——量级不算大,而且不稳定；
- **正确性**：用 24 帧快速抽样比对（不同机位/不同时间戳），**24 帧里有 21 帧出现了差异**（改前是 0/24，改后的其它两处改动也都是 0/24）。抽查了一帧的具体差异：整帧 320 万个通道值里只有 2 个不同、差值都是 1/255——**单个差异幅度和已经接受的噪声同一量级,但出现的帧数从"整条 76 秒路线只有 1 次"变成"随手抽 24 帧就中 21 帧"**,这是本质不同的两件事。判断这个改动不能确定通过"逐值不变"的验收标准,**已撤销，不在这次改动里**。

这是本轮唯一一个"测出收益、但因为正确性风险主动放弃"的项。

### 6. 水面求交：专门看过，Newton 迭代次数不是瓶颈，加了一个安全的 XZ 预剪裁

`traceWater` 对每条可能穿过水面高度带的光线做最多 24 步安全 Newton 迭代（每步一次 `wave()`，即一次高度场缓冲读取 + 三次样条求值）。检查了两件事：

- **迭代次数是不是瓶颈**：把上限从 24 临时改成 4 或 12（仅用于测量，不是可交付改动，因为会让远处/陡峭波面提前放弃收敛，改变结果）测得 **-1.5% / -0.4%**——几乎没有差别,说明大多数光线要么在进入 Newton 循环前就被高度带/最大距离剪掉了,要么收敛得很快,**迭代次数本身不是这条路径的主要开销**。
- **水面 XZ 范围判断在 Newton 求解之后才做**（`traceWater` 最后才检查 `p.x>-7&&p.x<7&&p.z>-17&&p.z<10`），有些光线会白跑一整趟 Newton 求解,最后才因为落在房间范围外被丢弃。加了一个**精确的 XZ 预剪裁**：算出光线的 (x,z) 直线与水面矩形范围 `[-7,7]×[-17,10]` 的参数区间,如果这个区间和现有的高度带区间完全不重叠,直接提前返回空命中——**只在证明整个搜索区间必然失败时才提前退出,不缩小/改变实际喂给 Newton 迭代的区间**（避免了在多根情形下因为改变搜索括号而收敛到不同根的风险）。

**实测（同一浏览器会话交替测 3 轮）**：-0.2% / -2.5% / +10.7%（第三轮 sim 桶同时跳变，判断是环境噪声，不采信）。**收益不大**，原因是房间本身的墙壁边界基本就是 `[-7,7]×[-17,10]`——大多数会跑 Newton 求解的光线本来就已经在这个范围内被墙挡住或本来就在范围里,能被 XZ 预剪裁额外挡掉的光线不多。仍然保留这条改动,因为它是精确、零风险、且在某些机位下确实有几个百分点的收益。

### 累计效果与正确性验证

三条改动（`r.z`/`r.w` 死代码、恒等旋转矩阵、水面 XZ 预剪裁）全部落在 `src/render/common.wgsl`。用同一条 76 秒 / 2280 帧漫游路径，与本轮之前的状态（`git show HEAD:...`）逐值比对：

**607,027,200 个亮度值，改动前后完全相同，0 个不同**（比第一轮的"1 个差 1/255"更干净——这三条都是纯代数恒等变换/剪裁,不涉及浮点运算重新结合）。每 10 秒采样的 5 张标准截图逐字节相同。

采样数量、光线数量、光能公式：未触碰,只改了 `common.wgsl` 一个文件,`traceWater`/`tileProfile` 的输入输出契约不变。

### 结论：确认没有更多结构性空间,目标仍未达成

按用户列的六个方向逐项查完：BVH/访存（推理确认场景规模太小、不测）、占用率（实测排查,8×8 已经是最优附近）、重复工作（找到并修了两处真实浪费）、可预计算（查到一处理论可行但会破坏精确阴影边界,主动放弃）、数值简化（测到收益但改变太多像素值,撤销)、水面求交（专门测过,迭代次数不是瓶颈,加了一个小的安全剪裁)。

在"不许降采样数/光线数/光能公式"这条约束下,**目前找到的、且不改变任何输出值的优化,总共只能再挤出相机通道大约 5-6% 的耗时**（`r.z`/`r.w` 死代码约 -4%,其余几条各 0-2%)。这次没有找到能带来数量级改善的结构性空间——根本原因还是第一轮就定位到的那句话没变：**相机通道 89% 的开销是"采样数 × 光线数"这个乘积本身**,这个量级的差距（70% 档需要相对当前再快 2 倍以上）,不存在能在"不改变任何计算结果"的前提下达成的算法或调度技巧,只能来自减少这个乘积——而这正是硬约束保护的量。**70% ≥ 40fps、100% ≥ 30fps 依然没有达成,判断在当前约束下也不会达成。**
